## はじめに：RAGは「記憶」ではなく「検索」である

AIエージェントを長期運用する際、多くの人が最初に試すのが **RAG（Retrieval-Augmented Generation）** です。
ドキュメントをチャンクに切り、ベクトルDBに突っ込み、類似度検索（top-k）でコンテキストに注入する——非常に強力でポピュラーな手法ですが、**エージェントの「記憶」としては致命的な限界**があります。

* **セッションを跨ぐ同一性（アイデンティティ）が維持できない**
* **古いノイズや矛盾した情報が永遠に残り続ける（忘却がない）**
* **知識と主観（エピソード）が混ざり、人間のような学習・再統合が起きない**

本記事では、この課題を解決するために構築した **「複合記憶モデル（Composite Memory Architecture）」** と一般的なRAGを、構造・運用・リスクの観点から比較・解説します。

---

## 1. 複合記憶モデルの正体（4層構造）

今回構築したシステムは、人間の認知プロセス（記銘・想起・忘却・固定化）を模した4つのサブシステムで構成されています。

```text
┌────────────────────────────────────────────────────────┐
│                   AI Agent (はくあ)                   │
└───────────┬────────────────────────┬───────────────────┘
            │ (cue / recall)         │ (sanitize / save)
            ▼                        ▼
┌────────────────────────┐  ┌────────────────────────┐
│  Ebbinghaus Engine     │  │  Obsidian Wiki         │
│  - 忘却曲線 / 再定着     │  │  - 人間が読める外部記憶 │
│  - 活性 / アーカイブ制御 │  │  - Gitによる変更追跡    │
└───────────┬────────────┘  └───────────┬────────────┘
            │                        │
            ▼                        ▼
┌────────────────────────┐  ┌────────────────────────┐
│  Semantic Graph        │  │  CodeGraph             │
│  - 6k+ nodes / 4k+ links│  │  - AST/コード構造解析   │
│  - 全文検索 / 意味リンク │  │  - 開発コンテキスト保持 │
└────────────────────────┘  └────────────────────────┘
```

| 層 | 役割 | 実装・機能の備考 |
|---|---|---|
| **Ebbinghaus** | 語想起(cue)・睡眠統合・忘却・再定着 | 活性2,151件 / アーカイブ459件。Salience（重要度）とValence（感情度）で衰退率を制御 |
| **Obsidian Wiki** | サニタイズ済み外部長期記憶 | Git管理。`diary/` (エピソード), `dreams/` (内省), `concepts/` (意味知識) に分離 |
| **Semantic Graph** | グラフ検索・意味リンク・FTS | 6,265 nodes / 948 edges / 4,360 memory links。文脈のネットワーク関係を保持 |
| **CodeGraph** | コード構造の外部記憶 | `.codegraph/codegraph.db` によるAST・依存関係の暗黙的保持 |

## 2. 複合記憶モデル vs 一般的な RAG

RAGと本複合記憶モデルの違いを軸ごとに整理した比較表が以下です。

| 比較軸 | 複合記憶モデル (Composite Memory) | 一般的な RAG (Vector Search) |
|---|---|---|
| **記憶の構造** | エピソード ＋ 意味 ＋ 外部知識の3層分散構造 | ドキュメントを固定チャンク化して単一ベクトル化 |
| **想起トリガー** | Cue Vector (疎コサイン) ＋ グラフ探索 ＋ 全文検索 | Vector Embedding のコサイン類似度 top-k |
| **時間ダイナミクス** | 忘却曲線・睡眠サイクル・再リハーサルを組み込み | 基本的に静的（Static）。更新は再インデックス |
| **同一性の継続** | 記憶の変容と引き継ぎにより「エージェントの同一性」を維持 | セッション毎に断絶。過去のコンテキストは持ち越せない |
| **プライバシー制御** | サニタイズ処理 → Obsidian → Git による多段防御 | ベクトルDBに生テキストがそのまま残りやすい |
| **監査可能性 (Audit)** | Markdown ＋ Git Commit History で全履歴を人間が追跡可能 | 高次元Embedding空間はブラックボックスで解釈困難 |
| **関係性の保持** | ノード / エッジ / メモリリンクで明示的に意味関係を接続 | 単なる類似度プロットであり、論理関係を持たない |
| **自己適応** | Salience / Valence / Rehearsal による動的な強度補正 | 人間によるデータ書き換え・チューニングが主 |
| **検索パス** | 多経路ハイブリッド（Cue ＋ Embedding ＋ Graph ＋ FTS） | 基本的に Embedding 単体（またはシンプルなBM25複合） |
| **システム複雑さ** | **極めて高い** | **低い（ライブラリで完結）** |

## 3. 複合記憶モデルがもたらす3つの圧倒的利点

### ① 時間の経過と「能動的忘却」によるノイズ撲滅
一般的なRAGでは、1年前の古いFAQも昨日のデータも対等に検索対象になります。複合記憶モデルでは、アクセスされない記憶の Salience（重要度）が**エビングハウスの忘却曲線**に従って減衰し、自動的にアーカイブ層へ退避されます。これにより、長期間運用してもコンテキストウィンドウが不要なノイズで埋まりません。

### ② Git ＋ Markdown による完全な可視化と監査性
ベクトルDBの中身を人間が覗いて「なぜこの回答になったか」を調査するのは困難です。複合記憶モデルは外部記憶の正体を **Obsidian (Markdown) ＋ Git** に置いているため、いつどんな思考やログが追加・サニタイズされたかを `git log` や diff で100%追跡できます。

### ③ エピソード記憶（diary/dreams）と意味記憶（concepts）の分離
「自分が何を実行しどう感じたか（主観）」と「客観的な技術知識（事実）」を分けることで、人間のような内省（睡眠バッチ処理による概念の抽象化）が可能になります。

---

## 4. 導入にあたって覚悟すべきトレードオフ（欠点）

もちろん、銀の弾丸ではありません。運用には以下の泥臭い課題が伴います。

1. **構築・運用コストの跳ね上がり**
   Ebbinghausエンジン、Obsidian同期、Semantic Graph構造、CodeGraph生成の4系統を維持する必要があり、単なる `pip install chromadb` の世界とは別物の設計コストがかかります。
2. **定期バッチ（睡眠サイクル）の強制**
   記憶の再エンコード、スコア減衰、Gitコミット＆プッシュを裏でCronやTask Schedulerで回す必要があり、環境依存の問題（Windows Store Pythonスタブとの競合など）に直面しやすいです。
3. **マルチパス検索のチューニング難度**
   Cue・グラフ・FTS・Embeddingのスコア合成比率の調整を誤ると、意図しない過去の記憶を引っ張ってくる「フラッシュバック」現象が起きます。

---

## 5. 結論：RAGと複合記憶はどちらを選ぶべきか？

明確な使い分けの答えは以下になります。

* **静的なドキュメント検索・マニュアル回答・FAQ** ➔ **RAG が圧倒的に優位**（手軽で高速）
* **長期稼働するAIエージェントの人格・同一性・文脈維持** ➔ **複合記憶モデル が不可欠**

### ベストプラクティス：二層アーキテクチャの併用

最も現実的な構成は、**両者を役割分担させること**です。

* **RAG** ➔ エージェントが参照する「外部ライブラリ・辞書」
* **複合記憶モデル** ➔ エージェント自身の「脳（アイデンティティ・過去の経験・関係性）」

RAGで限界を感じているエージェント開発者は、「ベクトル検索の精度を上げる」アプローチから一歩進んで、**「時間・忘却・関係性を考慮した記憶基盤」** の設計にチャレンジしてみてはいかがでしょうか。
